# Test Requirements: Windows App Deployment Pipeline

## Automated Tests

These criteria can be verified through scripted tests (PowerShell/Pester or shell scripts) that run on a Windows machine or in CI.

| AC ID | Description | Test Type | Approach |
|-------|-------------|-----------|----------|
| AC1.2 | Release includes SHA256 checksum file matching zip contents | Integration | After CI run, download both assets via `gh release download`, recompute `Get-FileHash` on zip, compare to `.sha256` file contents. Can run as a post-release CI job or local script. |
| AC1.3 | Release excludes `appsettings.json` and `models/` from zip | Integration | Download release zip, expand to temp dir, assert `appsettings.json` and `models/` do not exist in extracted contents. Scriptable via `Expand-Archive` + `Test-Path`. |
| AC1.4 | Default `appsettings.json` attached as separate release asset | Integration | Query release assets via `gh api repos/{repo}/releases/latest` and assert `appsettings.default.json` is present in the asset list. |
| AC1.5 | `dotnet list package --vulnerable` runs and fails build on vulnerable packages | Integration | Verify the workflow YAML contains the vulnerability scan job. Full verification requires AC1.7 (see Human Verification). |
| AC1.6 | All GitHub Actions pinned by commit SHA | Unit | Parse the workflow YAML, extract all `uses:` values, assert each matches `owner/action@<40-char-hex-sha>` pattern. Scriptable with Python or PowerShell regex. |
| AC2.2 | User's `appsettings.json` and `models/` preserved across deploy | Integration | Pre-deploy: write a sentinel value into `appsettings.json` and create a dummy file in `models/`. Run deploy. Post-deploy: assert sentinel value and dummy file still exist. Requires a real release artifact. |
| AC2.4 | Deploy verifies SHA256 checksum before extracting | Integration | Run deploy against a valid release, capture output, assert log contains checksum verification message. Pair with AC2.5 for negative case. |
| AC2.5 | Deploy rejects artifact with mismatched checksum | Integration | Download release assets to temp dir, overwrite `.sha256` with a bogus hash, invoke `deploy-app.ps1` pointing at the tampered temp dir (or mock the download step). Assert script exits non-zero with checksum mismatch error. |
| AC2.6 | Deploy refuses to write outside install directory | Unit | Call `Assert-PathWithinInstallDir` directly with paths containing `..` that escape the install dir. Assert it throws. Also test with a valid path to confirm it passes. Pester test against the function. |
| AC3.2 | Model download retries 3x with backoff on network failure | Integration | Temporarily set an invalid model URL in a test copy of `app-registry.json`. Run deploy. Assert output shows 3 retry attempts with increasing delays and a clear final error message. |
| AC3.3 | All deploy actions logged to timestamped audit file | Integration | Run a full deploy cycle, then read `%USERPROFILE%\Apps\deploy-log.txt`. Assert file exists, contains timestamped entries for key steps (download, checksum, extract, start), and includes the app name. |
| AC3.4 | Deploy skips stop step gracefully when app is not running | Integration | Ensure the target process is not running before deploy. Run deploy. Assert output contains "not running" or equivalent skip message and deploy completes successfully. |
| AC4.3 | Bootstrap is idempotent | Integration | Run `bootstrap-deploy.ps1` twice in sequence. Assert no errors on second run, no duplicate `.bat` files, tools directory contents are unchanged, and output indicates "already exists" for `.bat` files. |
| AC5.3 | Each app's config and models are isolated in separate directories | Integration | After deploying both whisper-service and systts, assert `%USERPROFILE%\Apps\WhisperService\` and `%USERPROFILE%\Apps\SysTTS\` each contain their own `appsettings.json` and model files with no overlap. |

## Human Verification

These criteria require manual observation on a real Windows machine with GitHub integration, and cannot be reliably automated due to external dependencies, GUI interaction, or end-to-end infrastructure requirements.

| AC ID | Description | Why Not Automated | Verification Steps |
|-------|-------------|-------------------|-------------------|
| AC1.1 | Push to `main` triggers Windows runner build, produces GitHub Release with zip artifact | Requires a real push to `main` on GitHub and observing the Actions tab. CI trigger behavior is a GitHub platform feature, not locally testable. | 1. Merge a PR to whisper-service `main`. 2. Open GitHub Actions tab, confirm `Build and Release` workflow starts on `windows-latest`. 3. After completion, check Releases page for new release with zip asset. |
| AC1.7 | Build with known-vulnerable NuGet package fails CI before release creation | Requires intentionally introducing a vulnerable package into a real .NET project and pushing to trigger CI. Destructive to the project state if not carefully managed. | 1. Create a test branch. 2. Add a known-vulnerable NuGet package (e.g., an old version of `System.Text.Json` with a CVE). 3. Push and trigger CI via `workflow_dispatch`. 4. Confirm the `vulnerability-scan` job fails and no release is created. 5. Revert the change. |
| AC2.1 | `deploy-app.ps1 -App whisper-service` downloads latest release, extracts, and starts the app | Requires a real GitHub Release, real Windows process start, and `gh` CLI authentication. Full lifecycle depends on external services (GitHub API, network). | 1. Open PowerShell on Windows. 2. Run `deploy-app.ps1 -App whisper-service`. 3. Observe download, extraction, and process start in output. 4. Confirm `WhisperService` process is running via Task Manager or `Get-Process`. |
| AC2.3 | First-time deploy installs default `appsettings.json` and downloads required models | Requires a clean machine state (no prior install) and network access to Hugging Face for model download. Model downloads are large and time-dependent. | 1. Delete `%USERPROFILE%\Apps\WhisperService\` if it exists. 2. Run `deploy-app.ps1 -App whisper-service`. 3. Confirm `appsettings.json` was created from `appsettings.default.json`. 4. Confirm model file exists in `models/` directory. |
| AC2.7 | Fresh machine deploy completes successfully including model download | Same as AC2.3 but emphasizes the full fresh-machine scenario including no prior tooling. Cannot be automated without a disposable VM or container. | 1. On a machine with no prior installs, run `bootstrap-deploy.ps1` then the `.bat` file. 2. Confirm full cycle: tooling copied, release downloaded, app installed, models downloaded, app running. |
| AC3.1 | Failed deploy at any step restores backup and restarts previous version | Requires a successful prior deploy (to have a backup), then inducing a failure mid-deploy. The failure injection point varies (network, disk, permission) and the rollback must restore a running process. | 1. Complete a successful deploy of whisper-service. 2. Induce a failure: either tamper with the checksum (easiest), disconnect network mid-download, or make install dir read-only. 3. Confirm previous version's `appsettings.json` and binaries are restored. 4. Confirm the old version's process is restarted and running. |
| AC4.1 | Double-clicking `.bat` file on desktop runs full deploy cycle with visible output | Requires GUI interaction (double-click) and visual confirmation of a cmd.exe window with deploy output. Cannot be scripted without GUI automation tools. | 1. Double-click `Deploy whisper-service.bat` on Desktop. 2. Observe cmd.exe window opens with title "Deploy whisper-service". 3. Confirm deploy output is visible and window stays open at `pause` prompt. 4. Confirm app is running after completion. |
| AC4.2 | `bootstrap-deploy.ps1` copies tooling to `%USERPROFILE%\tools\` and `.bat` to Desktop | While file existence is scriptable (see AC4.3), the first-run experience on a fresh machine with correct paths and permissions requires manual verification. | 1. Run `bootstrap-deploy.ps1` from the claude-env repo. 2. Confirm `%USERPROFILE%\tools\deploy-app.ps1` exists. 3. Confirm `%USERPROFILE%\tools\app-registry.json` exists. 4. Confirm `.bat` files appear on the Windows Desktop. |
| AC5.1 | Adding a new app requires only a registry entry, CI workflow, and `.bat` file | This is a process/design criterion, not a runtime behavior. Verification is confirming that no script modifications were needed for SysTTS onboarding. | 1. Review the SysTTS onboarding diff (Phase 5). 2. Confirm changes are limited to: `app-registry.json` (new entry), `SysTTS/.github/workflows/build-release.yml` (from template), and bootstrap creating the `.bat`. 3. Confirm `deploy-app.ps1` was NOT modified. |
| AC5.2 | SysTTS deploys via the same pipeline as whisper-service with no script modifications | Requires SysTTS to have a real CI-produced release and a real Windows machine to deploy on. End-to-end validation of the general-purpose claim. | 1. Ensure SysTTS has a CI-produced release on GitHub. 2. Run `deploy-app.ps1 -App systts` on Windows. 3. Confirm download, install, model download (Piper voices + espeak-ng-data), and app start all succeed. 4. Confirm `deploy-app.ps1` has zero SysTTS-specific code. |
